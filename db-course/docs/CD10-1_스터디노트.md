## 1. 교안 4번 슬라이드 – 현업 사례: AWS RDS Proxy
- 상황: 수강신청 시작 직후 1,000명 동시 접속 (**1,000명은 수업용 가정**)
- **공개 사례:** RDS Proxy는 DB 연결을 풀에 두고 재사용. 트랜잭션이 끝나면 연결을 반환해 다른 클라이언트가 씀.
- **연결 고정(pinning):** 클라이언트가 `SET`, 임시 테이블, Prepared Statement처럼 세션 상태를 바꾸면 그 연결은 남과 나눌 수 없어 Proxy가 해당 클라이언트에 묶어 둠 → 고정이 많아지면 풀링 효과 사라짐.
- **"교안 연결" 행의 의미:** 기술 용어가 아니라 "이 사례가 교안의 어느 개념과 연결되는가"라는 뜻. 연결되는 개념은 *직접 연결하면 연결 1개마다 백엔드 프로세스 1개 생성* (2. Server Processes).
- 출처: https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.howitworks.html

### 흐름도 요약
| 흐름 | 경로 | 결과 |
|---|---|---|
| ① 직접 연결 | 학생 1,000명 → RDS | 백엔드 프로세스 1,000개 → max_connections·메모리 한계 |
| ② 연결 풀링 | 학생 1,000명 → RDS Proxy → RDS | 백엔드 수십 개로 처리 |
| ③ 연결 고정 | 세션 상태 변경 → Proxy가 연결 고정 | 공유 불가, 풀링 효과 감소 |

## 2. Q. RDS Proxy는 PostgreSQL을 AWS에 직접 설치하는 구성인가?
- 아니다. **AWS 관리형 RDS PostgreSQL 앞에 관리형 서비스 RDS Proxy를 하나 더 두는 구성**: 앱(EC2·Lambda) → Proxy 엔드포인트 → RDS.
- EC2에 PostgreSQL을 직접 설치하면 RDS Proxy를 쓸 수 없고 **PgBouncer**를 직접 설치해야 함.
- **RDS Proxy는 VPC 내부 전용**이라 Colab이나 집 PC의 pgAdmin에서는 접속할 수 없음 → 수업에서는 실습이 아니라 현업 구조를 설명하는 사례로 사용.

## 3. Q. 흐름도의 "SELECT"는 무엇인가?
- 앱이 DB에 데이터를 요청하는 **조회 SQL 문장 하나**.
```sql
SELECT course_name, professor, seats_left
FROM courses WHERE dept = '컴퓨터공학' AND seats_left > 0;
```
| 구분 | ① 연결 수 문제 | ② 느린 SELECT 문제 |
|---|---|---|
| 상황 | 1,000명 동시 접속 | SELECT 1문장이 3초 걸림 |
| 원인 | 백엔드 프로세스 과다 | 비효율적 실행 방법(예: 인덱스 없이 전체 읽기) |
| 담당 | Server Process | Planner(방법 선택) → Executor(실행) |
| 해결 | RDS Proxy, PgBouncer | 인덱스, 쿼리 수정, ANALYZE |
| 확인 | pg_stat_activity 연결 수 | EXPLAIN ANALYZE |
- 비유: Proxy는 웨이터를 효율적으로 돌리는 것. 요리 하나가 30분 걸리면 웨이터를 늘려도 30분 → 조리법(실행계획)을 바꿔야 함.

## 4. Q. Executor는 AWS 기능인가?
- 아니다. **PostgreSQL 내부의 SQL 처리 5단계 중 마지막 단계** (Parser → Analyzer → Rewriter → Planner → Executor).
- Planner가 정한 계획대로 테이블·인덱스를 읽고 필터·정렬·집계 후 결과 반환.
- 로컬·EC2·RDS 어디서나 동일하게 동작.

| PostgreSQL 자체 | AWS 서비스 |
|---|---|
| Parser·Planner·Executor, 백엔드 프로세스, WAL | RDS(설치·백업·패치 대행), RDS Proxy(연결 풀링) |

## 5. Q. WAL은?
- **Write-Ahead Log(선행 기록 로그)**, PostgreSQL 자체 기능. 데이터 파일보다 변경 기록(로그)을 먼저 디스크에 남김.
- 처리 순서: ① WAL 버퍼(메모리)에 기록 → ② 커밋 시 WAL Writer가 WAL 파일에 기록(저장 보장) → ③ 데이터 파일 반영은 나중에 Checkpointer가 처리.
- 장애 시 WAL을 다시 적용해 복구 → ACID의 D(지속성) 보장.
- 비유: 장부(데이터 파일)를 고치기 전에 거래 전표(WAL)를 먼저 써 둠.
- AWS의 자동 백업, **특정 시점 복구(PITR)**, **읽기 복제본**은 WAL을 활용한 기능.
- 관련 사례: Uber(2016) – UPDATE가 많으면 새 행 버전 + 인덱스 갱신 + WAL 기록이 늘어나는 쓰기 증폭 문제.

## 6. "연결 1개 = 백엔드 프로세스 1개"를 눈으로 보여 주는 방법
1. **Windows 작업 관리자(가장 효과적):** 세부 정보 탭에서 `postgres.exe` 개수 확인 → pgAdmin Query Tool을 하나 열 때마다 1개씩 증가.
2. **pgAdmin 대시보드:** Server sessions 그래프와 Sessions 목록의 PID 확인 (RDS도 가능).
3. **Colab:**
```python
conns = []
for i in range(10):
    conns.append(psycopg2.connect(**cfg))
    cur = conns[0].cursor()
    cur.execute("SELECT count(*) FROM pg_stat_activity WHERE backend_type='client backend'")
    print(f'연결 {i+1}개 → 백엔드 {cur.fetchone()[0]}개')
for c in conns: c.close()
```
4. **그림 자료:**
   - PostgreSQL 공식 문서 "How Connections Are Established": https://www.postgresql.org/docs/current/connect-estab.html
   - The Internals of PostgreSQL 2장 "Process and Memory Architecture": https://www.interdb.jp/pg/pgsql02.html
